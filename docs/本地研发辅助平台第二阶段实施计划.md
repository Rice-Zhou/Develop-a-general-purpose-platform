## Global Constraints

- 每台开发电脑独立运行；项目、人员、来源与模型通过配置表达。
- SQLite 是配置、任务和报告元信息的唯一权威记录。
- 分析前自动更新配置分支，随后固定 SHA 和文档快照；同步失败不得使用过期材料继续。
- 禁止自动 stash、reset、clean、checkout、rebase 或创建合并提交。
- 核心单测单例超时 60 秒；Git 同步超时 5 分钟；普通 HTTP 请求超时 30 秒；AI 任务总上限 20 分钟。
- 首版全局串行调度，第二阶段复用现有队列、取消、重试与崩溃恢复，不另建分析任务队列。
- 不读取既有登录凭据、不构建仓库、不运行仓库脚本、不推送、不操作 Jira/Trinity。
- 密钥只通过应用设置提交并由主进程 safeStorage 保存；返回 Renderer 的配置不含密钥。
- 未取得供应商、模型或飞书访问配置时，相应远端能力显示待配置，不以测试替身代替实际调用，不宣称完成真实联调。
- 原始材料和模型输出属于不可信数据；不得修改权限、访问其他项目或调用通用 Shell。
- 第一阶段数据必须可升级；备份失败则不得修改 schema。旧代码快照仍能读取。

## 范围与接入条件

第二阶段完整目标包含 DOCX、文本 PDF、飞书、检索、需求候选提取与人工修订、手动核对、一个真实 API 执行器、证据详情与 Markdown 导出。

执行顺序先完成本地文档与证据基座，再连接远端。即使暂时没有外部账户，本地文档读取、解析质量提示、固定快照检索和人工需求管理也须可以独立运行。

首个 API 协议建议使用明确标识的 `chat-completions` 适配器，base URL、供应商名称、model、凭据引用由配置提供；只支持实际通过契约的该协议，不宣称通用于所有模型。供应商和模型由用户确认及实际能力测试决定。飞书建议先支持企业自建应用，应用权限、访问主体和文档授权分别检查；若实际选择用户授权，需要在任务 4 开始前调整认证实现，不能借用浏览器会话。

目前缺少真实模型和飞书访问配置，已向用户询问；缺口只阻止对应连接器的启用和真实联调，不阻止本地基座实现。凭据不应通过聊天或仓库提供。没有真实联调证据时，只能报告相应模块的本地或协议测试通过，第二阶段整体退出条件保持未满足。

## Review Focus

1. 解析损失：图片、扫描页、乱码、表格合并和未知飞书块必须可见；受影响需求不能判为缺失或已实现。任务 3、4、6。
2. 材料变化：本地读取中变化或飞书分页期间版本变化，不能发布混合快照；必需资料失败阻断分析，可选失败记录缺口。任务 2—4。
3. 项目越界：相同文件名、伪造块 ID、路径穿越和旧上下文证据不能混入当前项目；读取、搜索和模型工具使用同一权限入口。任务 5、6。
4. 数据迁移与完成一致性：旧 v1 数据升级、取消、崩溃和模型无效输出不得留下成功任务或半份报告。任务 1、6。
5. 外发与密钥：未关联来源、重定向、伪造工具调用和含密钥错误响应不能扩大读取或泄露凭据；认证失败保持可见。任务 4、6、7。

## 公共协议与边界

新增 `packages/contracts/src/documents.ts`、`requirements.ts`、`analysis.ts`，保留现有 `models.ts` 的通用类型。协议对象统一携带 `schemaVersion: 1` 和实现版本；应用内部 ID 使用 UUID。

| 类型 | 必需字段 |
| --- | --- |
| DocumentSnapshot | id、schemaVersion、projectId、bindingId、kind、sourceLocator、contentHash、sourceRevision、parserVersion、fetchedAt、blocks、warnings |
| DocumentBlock | id、kind、text、headingPath、anchor、table、warnings；anchor 根据来源区分段落、PDF 页码及坐标、飞书 blockId |
| SourceGap | bindingId、code、message、required、affectedBlockIds |
| RequirementSet | id、projectId、contextSnapshotId、revision、createdAt、items |
| RequirementItem | id、text、acceptanceCriteria、sourceRefs、clarification、reviewed |
| EvidenceRef | id、projectId、contextSnapshotId；代码证据包含 bindingId、commit、path、startLine、endLine、snippetHash，文档证据包含 documentSnapshotId、blockId、quoteHash |
| AnalysisReport | id、schemaVersion、projectId、taskId、attemptId、contextSnapshotId、requirementSetId、inputSnapshotIds、executorVersion、templateVersion、createdAt、findings、evidenceRefs、limitations、sourceGaps、usage |
| Finding | requirementId、status、explanation、evidenceIds、checkedScope、verification；status 为 IMPLEMENTED、PARTIAL、MISSING、UNKNOWN、CONFLICT |
| AIProfile | id、protocol、baseUrl、model、credentialRef、outboundEnabled、requestBudget；凭据引用不等于授权外发 |

`ContextSnapshot.documents` 从 `never[]` 变为 `DocumentSnapshotRef[]`，并增加可选 `sourceGaps`。读取旧上下文时通过版本解析显式识别 legacy，不把旧“仅代码准备成功”解释为已读取文档。

任务沿用现有 attempt 计数，新增稳定 `attemptId`；旧记录通过确定性迁移赋值。Task.kind 扩展 PREPARE_CONTEXT、EXTRACT_REQUIREMENTS、CHECK_REQUIREMENTS；状态补充 RUNNING、VALIDATING，仍使用同一个 TaskService 调度。任务输入保存项目修订及需求版本，重试形成新尝试并重新准备上下文；提取或核对过程中不悄悄替换输入。

## 自查与执行交接

接口依赖顺序：协议/迁移 → 文档获取 → 本地解析与飞书 → 快照访问/检索/需求版本 → 分析流水线 → UI → 打包验收。新任务类型必须接入已有调度器；读取/检索/模型工具必须共享 ContextReader；报告成功必须只在一个事务入口表达。

五项 Review Focus 均有目标测试。第二阶段覆盖完整需求闭环，未将 Jira/Trinity 或自动监控提前混入。真实供应商、模型、飞书访问主体尚待确认，能力未验证时显示不可用；这不影响前五项本地工作推进。

执行方式沿用用户已选的当前会话直接开发，不再重新询问。按 writing-plans 的交接要求，本新增实施计划需先供用户评审；确认范围与协议选择后连续推进，无需逐任务再确认。

参考实现文档：[Mammoth](https://github.com/mwilliamson/mammoth.js)、[PDF.js API](https://mozilla.github.io/pdf.js/api/)、[飞书文档块接口](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/list)。
