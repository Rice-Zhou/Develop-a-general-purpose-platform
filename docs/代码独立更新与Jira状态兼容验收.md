# 代码独立更新与 Jira 状态兼容（0.5.0）

## 交付内容

项目管理中的按钮改为“更新代码”，提交独立代码任务，复用现有全局串行队列。该任务仅更新项目配置的仓库和分支，不读取需求文档、构建索引或创建分析上下文，因此必需文档缺失不会阻断代码更新。需求核对页仍保留“准备文档上下文”。任务历史及详情区分代码更新和上下文准备。

更新通过 fetch 后快进或 rebase 完成，相当于对配置分支进行 pull/rebase；保留本地提交，不自动 stash、清理工作区或 push。分支不匹配、工作区未提交修改、跟踪缺失等仍明确停止。开始 rebase 前保存本地提交备份引用，并记录本轮分支、原提交及目标提交。

Rebase 冲突进入等待处理并弹窗，可选自行解决或 AI 解决并继续。自行处理需编辑文件、git add，再点击继续；也可稍后处理或在仓库 git rebase --abort。一个 rebase 中后续提交再次冲突时，会再次暂停等待选择，不把处理一个冲突当作全部完成。已被后续更新任务替代的旧冲突不会在启动时自动弹出。

AI 按钮只有在项目关联有效 AI 连接且允许发送材料时才启用；后台也校验配置。复用现有 API / 订阅执行连接及其独立代理配置，仅提供冲突材料，模型不获得项目工作目录的命令工具。返回的文件清单必须精确覆盖当前冲突集，拒绝其他路径和残留冲突标记；写入前校验项目版本、连接、HEAD、索引和原文是否变化，并拒绝路径越界、符号链接、硬链接、二进制及过大文件。应用只暂存返回的冲突文件并继续 rebase，不推送。文本处理限制为 1～10 个普通 UTF-8 文件，每个原文件最多 128 KiB；不支持的冲突明确交给用户处理。

平台只接管自己发起且分支、原提交和目标提交匹配的 rebase。任务取消、应用退出或处理失败时可能保留暂停状态及已完成步骤，不自动重置用户工作树；任务错误与 Git 状态可供继续检查。原分析前同步仍使用原有远端固定版本限制。

## Jira 根因与修复

截图中实际请求已到达 Jira，服务端明确返回“status 域中没有分配中值”的 400。根因是 JQL 写死三个中文状态名，只要实例缺少其中一个，整条查询就失败，与此前失效连接的错误不同。

Jira CLI 没有完整状态目录读取命令。新版共享 JQL 只按配置实例、项目、负责人和缺陷类型读取，使用问题详情返回的实际状态由核心服务统一严格索引“修复中、分析中、分配中”。没有猜测其他状态名，也没有将 400 当作成功空列表。完成状态不会进入缓存索引、工作台或 AI 预分析；范围查询可能读取其元信息，原分页和数量上限仍适用于整个配置范围。

2026-10-20 使用本机已经配置的 CLI 及选中项目，执行新版真实 Jira 适配器的只读完整分页及详情校验：`E0VPHEV` 范围返回 1 条问题，实际状态为“完成”，索引结果为 0 条。项目和负责人校验通过。该结果意味着当前范围无符合索引状态的问题，应显示成功空结果。未修改 Jira 单据、未保存问题原始正文，未更新实际业务代码目录。

## 验证

- 新增 Git 更新和 Jira 状态查询回归先确认旧实现失败：缺少 update 方法、JQL 包含不存在的状态常量。修复后通过。
- 固定产品源码后的全量单测 45 个文件、125 项通过，耗时 440.80 秒，包含原生 Jira CLI；TypeScript、ESLint、Windows make 通过。
- 最终包 4 条桌面回归通过：BUG 刷新及链接、原有 Jira CLI 证据预分析和 Trinity 转派校验、项目独立代码更新及重启、手动与 AI 冲突选择。代码更新用例故意关联不存在的必需文档，仍能完成更新且上下文保持为空。
- AI 用例覆盖同一次 rebase 的多轮冲突，每轮明确点击后才继续，核对模型调用数与用户提交的处理任务数一致。最初错误地假定一个 rebase 只有一轮冲突，后按真实提交重放语义修正用例；未放宽单次调用去重断言。旧 BUG 回归首次在截图阶段超时，重跑完整流程通过，不将超时轮次记作通过。
- 单测与桌面测试全部使用临时仓库、本机模型契约服务器和隔离数据目录。未调用真实付费模型，不发送真实飞书消息，不对实际业务仓库进行 rebase。
