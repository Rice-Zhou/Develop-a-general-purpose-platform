## 已实现行为

- 连接与项目分离：设置页创建 Jira CLI / Trinity 来源连接，项目绑定显式关联连接、实例、远端项目、稳定负责人和 BUG 类型。
- Jira 使用固定 `serverinfo`、`issue list`、`issue view` 命令；主进程不提供通用 Shell。列表 JQL 只含项目、负责人和类型过滤，由 CLI 的 `--order-by key --reverse` 设置唯一排序。列表只取编号，再逐条读取原始详情并走同一个 ScopePolicy。
- 每次命令前检查用户指定 CLI 配置中的非秘密 `server` 元信息与实例匹配；不保存或输出配置其余内容。`serverinfo` 校验部署类型，问题原始详情的 `self` 再次校验实例。逐页读取，处理重复页、输出预算和命令失败；仅将 CLI 1.7.0 的精确空结果退出契约解释为合法空页，其他失败仍报错。所有页及问题通过后才发布该绑定的新批次。最多 100 页、5,000 条问题，每次命令 30 秒、输出 8 MiB；整个手动列表读取还有 5 分钟上限，大范围可能需要缩小。
- Trinity 只调用已知的 `GET /quality/bugRedux/getByBugId`，认证头由加密凭据代理提供；业务错误、字段不符或范围不符会报错。没有调用无已证实项目过滤条件的全账户 `assignToMe`。
- 不可变问题快照包含问题正文、已读取评论、附件元信息、远端版本、归属、更新时间、读取时间、来源配置指纹和内容指纹。当前展示批次只是对快照 ID 的引用；历史报告不依赖当前批次。
- 分析进入原有串行 TaskService。重新读取问题并确认范围后，验证并安全更新全部配置仓库，固定 SHA、清单与文档快照，随后调用已有 AI 执行器和受限证据工具。
- 模型执行前、完成后复查远端问题版本；问题变化或转出时不提交成功结果。项目与连接配置改变也会阻止继续外发和提交，取消/超时沿用已有状态机。
- 已知其他项目的 Jira 编号在启动任何 CLI 命令前直接拒绝。空模型输出、无代码证据的候选原因不能保存为成功报告；明确列出缺失信息而尚不能形成分析时，任务进入材料不足的等待处理状态。
- 报告区分代码事实和原因假设，包含复现条件、支持及反对证据、排查步骤、缺失信息、检查范围和限制。代码事实必须引用本次取得的代码证据；伪造或跨项目证据会拒绝，最多请求一次输出修正。
- 不自动修改 BUG、评论、负责人、状态或代码。报告明确属于静态预分析；当前分支可能与故障版本不同，不能据当前代码否定历史问题。
- schema v3 继续使用同一个 SQLite，v1/v2 升级先一致备份；BUG 报告和成功任务、上下文由已有 finish 入口在同一事务提交，失败回滚。
