# 0.4.0 多来源 BUG 汇总与飞书提醒

## 原因与行为

0.3.6 的 Trinity 列表读取是显式不可用的占位实现，工作台按平台禁用了其列表按钮，因而不能完整展示两个来源。原工作区读取还会因一个失效范围抛错而影响整页；按编号读取则替换该来源当前批次。

新版保留每个本地项目自己的项目及负责人范围，点击一次“刷新问题单”即可读取全部绑定来源，在同一列表中展示。单个来源读取或配置错误会显示该来源的错误及最近成功时间，其余来源仍正常展示。失败来源可显示上次缓存，但明确标为旧材料；不会用成功空列表掩盖读取失败。单号读取改为补充或更新对应问题，不删除其他问题或其他来源。不同连接的问题保持独立，不按相似标题跨平台合并。

Jira 继续复用已有 CLI 或账号连接及三种状态限制。Trinity 根据目标站点公开前端确认的 `POST /quality/quality/bug/findBugsByProject`，发送 projectId、projectIds、assignees、pageNum 和 pageSize，完成所有分页后才发布范围批次。分页重复、总数变化或不完整均明确失败；每条问题通过原有 detail 接口重读并验证项目、负责人和 BUG 类型，不调用全账户 assignToMe。单次分页最多 100 页、每页 100 条，整轮刷新有 5 分钟预算。

复查目标前端还发现，apiVersion/isGray 实际来自 `/sys/user/userinfo` 的当前账号返回值，旧适配器却固定为 V6.5.0。新版先获取并验证该元数据，再发送项目和详情请求，不再猜测版本；无法取得元数据时明确报错。测试验证返回 V7.5.0 时请求使用该版本，以及缺少元数据时完全不查询问题。

两个平台的详情链接统一由核心服务构造并校验，界面直接展示链接，无需按平台切换。Trinity 使用站点实际页面路由 `/#/bug/newBugDetail`，附带 projectId、id、bugId 及返回的 workitemId；Jira 保留实例上下文与 browse 单号路径。打开链接时后台再次验证当前项目归属。

## 调度、基线与通知

默认开启查询及通知，每 5 分钟核对已启用项目；工作台可以设置 1～1440 分钟、暂停查询及关闭通知。服务每 15 秒检查是否到期；同项目的手动刷新及后台查询合并为同一轮，来源并发最多为 2。首个成功完整批次建立基线，不提醒存量。后续首次观测到进入当前范围的问题时创建通知，已完成等非索引状态不会触发 Jira 通知。范围或连接配置变化重新建立基线。

基线、最近成功时间及待发送记录放在 SQLite settings 的单条监控状态记录中。一次观测和待发送记录一起持久化，再尝试发送。接口失败不推进该来源基线；其余来源独立推进。发送失败显示错误并保留待发送记录，下次该来源刷新成功后重试。暂停、删除项目或解绑来源后，不再为失效范围发送通知。

飞书适配器使用已配置的官方 CLI。通过 `api GET /open-apis/authen/v1/user_info --as user` 确认当前用户，再使用 `im +messages-send --as bot --user-id ...` 私信该用户，消息包含项目、问题号、标题和安全构造的详情链接，不含代码或文档。接收人首次确认后固定，发送前重新识别；切换 CLI 登录用户会停止发送并明确提示。发送前还再次检查项目与通知设置是否仍有效。

每条待发送记录有持久化 UUID，并作为 `--idempotency-key` 传入 CLI；收到有效 message_id 才移除记录。“检查飞书接收人”只读查询身份，不发送测试消息。缺少 CLI、用户授权或机器人消息权限时显示配置/发送错误。普通重复查询和重启可去重；远端已收到消息但进程在保存回执前崩溃的边界仍依赖飞书的幂等有效期，不声称跨任意时长严格恰好一次。通知批次有 30 秒预算，超时后保留剩余记录。

通知失败直接显示在折叠设置之外，摘要同时显示异常及待发送数量，避免折叠面板掩盖错误。

应用或托盘进程存活时调度，退出时先取消并等待读取、通知进程，再关闭数据库。休眠、关机或断网期间不能实时通知；恢复后按范围核对。两次查询之间发生又结束的中间变化不能保证捕获。此版本按用户要求实现新问题提醒，不自动启动 AI 分析，完整第四阶段的自动分析队列等仍未交付。

## 验证与边界

新增状态、汇总、分页、通知及调度回归均使用临时项目、本机服务、虚拟时钟或可执行 CLI 夹具。新增桌面用例在 0.3.6 确认失败：Jira 可见，Trinity 问题链接不存在。

最终包的 4 条桌面回归通过，耗时 2.3 分钟，覆盖统一汇总、来源失败隔离、原有 Jira CLI 更新代码与证据预分析、Trinity 转派阻止成功、通知错误在折叠设置之外可见，以及等待真实一分钟周期自动发现和提醒新增问题。通知测试使用临时编译的 CLI 夹具，仅记录命令和返回回执，不发送真实消息。类型检查、ESLint 和 Windows make 通过。

补强去重断言后，额外等待最后一次手动刷新和通知流程完整结束再核对发送次数；该桌面用例再次通过（1.4 分钟），仅两条新增问题各发送一次。

固定最终源码后的针对性单测 15 个文件、35 项通过，含分页、动态协议、范围隔离、通知回执、账号变化、失败保留、重启去重、调度及升级备份。迁移的两个文件随后再次独立重跑，10 项全部通过。此前一次全量 40 个文件、113 项通过；之后全量执行期间补了数据库升级保护，导致该轮测试服务缓存旧迁移实现，出现 3 条版本断言失败，不把该轮当作全量通过。重新启动后的存储回归已验证 v5 和 v4 备份。
