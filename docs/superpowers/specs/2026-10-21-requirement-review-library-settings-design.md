# 需求审核待办、独立资料分类与连接设置收拢设计

日期：2026-10-21。开发目录：D:/development/Develop-a-general-purpose-platform。

## 1. 目标和已确认交互

需求核对用于由当前项目实际生效的 AI 连接，检查当前代码对关联需求的覆盖情况，列出疑似未实现或部分实现项。AI 给出静态判断与依据，用户负责决定误报、确认未完成和确认完成。

用户已确认：

- 每条需求待办初始不预选分类，提供“误报 / 未完成”单选。
- 选择“误报”后，后台保存成功即从默认待办列表移除。
- 选择“未完成”后，勾选“确认未完成”才进入已确认状态，并显示“完成”选项；随后勾选完成、保存成功后移除。
- 已完成项后续再次检出缺失或部分实现时重新打开，重新进入待确认状态。
- 误报在同版需求内保持关闭；需求内容或来源引用发生实质变化后重新审核。

资料库可在没有任何代码项目时独立使用，保存需求、UI、UE、通用资料及路径、链接、文本；分类与关联项目是两件独立的事。设置页默认只展示已保存连接，用户主动新增或编辑才出现配置字段。

## 2. 现状与方案选择

现状：

- TaskService 中除 BUG 预分析外的上下文、需求提取和核对任务会执行 git.inspect/assertReady/synchronize，导致需求功能隐含拉取代码。
- RequirementsPage 无条件展示该项目最近任务的 error，可能把 BUG、日志下载和旧任务错误展示在“项目需求与原文”。
- 资料资源已经可独立保存，但只有 docx/pdf/feishu 三类，缺少层级分类和通用资料表达。
- 设置中的 IssueConnectionsPage 和 ConnectionsPage 始终渲染新增表单，进入设置即暴露大量字段和检测状态。

备选：仅修改界面文案与隐藏按钮成本低，但不能保存人工处理状态，也不能真正取消后台代码同步；另起一套知识库和任务系统会重复已有资源、报告和执行队列。

采用在现有报告、资源和执行队列上增加人工审核状态与分类的方案：报告是 AI 结论的唯一来源，审核状态只保存用户决定；资料只有一份规范存储；继续使用原任务队列执行 AI 审核。

## 3. 需求审核流程

### 3.1 当前代码与 AI

需求页面主操作收敛为“AI 审核当前代码”，展示实际生效 AI 连接。没有可用 AI 时说明原因，提供前往设置入口，不创建成功或空报告。

一次审核在执行队列中完成：捕获当前工作区（含未提交修改）→读取关联需求材料并固定快照→提取/复用经过新鲜度验证的需求→逐项审核→校验证据和来源→事务保存报告及更新待办。需求内容没有改变时复用同一语义需求身份，不能仅因重复提取产生新 UUID 就重复生成任务。

复用现有 captureCurrentCode/captureWorktree，不另做快照实现。需求上下文、需求提取、实现核对路径均不执行 fetch、pull、rebase 或 synchronize，也不拒绝正常的未提交修改。AI 审核期间代码/文档变化须显式停止或标记结果失效，不用过期报告覆盖新结果。

本设计将“删除更新代码逻辑”限定为需求相关工作流；项目管理中用户主动点击的“更新代码”继续作为独立手动操作。

保留原文阅读、人工修订需求和报告导出为二级功能；无代码项目时使用独立资料库，不在需求审核页面创建虚假代码项目。

### 3.2 哪些结论进入待办

- MISSING、PARTIAL：生成“疑似未实现”待确认条目，展示需求原文/验收条件、AI 说明、读取范围和代码依据。
- IMPLEMENTED：只计入审核结果，不新增未实现待办。
- UNKNOWN、CONFLICT：单独列为“信息不足 / 需求待澄清”，不伪装成确定的未实现项。
- 没有足够证据、资料读取失败、模型执行失败时明确显示失败或信息缺口，不能把未读取到代码当成已证明缺失。

未完成业务清单位于需求核对页面。一级“任务列表”仍只负责运行中的审核执行任务、取消及任务历史，不把人工需求条目伪装成后台执行任务，也不增加第二个执行队列。

### 3.3 人工状态与可见性

规范状态为待确认、已确认未完成、误报、已完成。首次检出总是待确认，不由模型代选“未完成”。

| 当前条目 | 用户操作 | 保存成功后的结果 |
| --- | --- | --- |
| 待确认 | 单选“误报” | 记录为误报，立即从默认列表消失 |
| 待确认 | 单选“未完成” | 展示“确认未完成”勾选框，仍留在列表 |
| 已选择未完成 | 勾选“确认未完成” | 保存为已确认未完成，展示“完成”勾选框 |
| 已确认未完成 | 勾选“完成” | 保存为已完成，从默认列表消失 |
| 已处理记录 | 点击恢复 | 返回待确认列表，重新由用户选择 |

分类选择与“确认未完成 / 完成”是不同控件，不能让一次勾选同时代表确认分类和完成开发。写入失败时原条目保留并展示当前项错误，避免界面假消失。已处理记录默认收起，保留选择、时间、对应报告和需求版本，支持恢复。

新报告不会替用户勾选完成。既有未完成项即使最新 AI 改判已实现，也仍展示“最新审核认为已实现，待人工确认”，直到用户处理。已完成项只有再次获得有效 MISSING/PARTIAL 结论才重新打开；UNKNOWN 或审核失败不触发重开。误报在同版需求内保持关闭，不能因为 AI 换了措辞又冒出一条相同待办。

### 3.4 唯一身份与并发

审核条目按代码项目和需求语义指纹隔离；指纹由关联资源稳定 ID、来源引用内容哈希、规范化需求文本及验收条件计算，不使用报告 ID、快照 UUID、AI 解释文案或当前列表序号。重复提取若内容与引用一致，不产生重复条目。不能用模糊标题匹配继承误报。

语义指纹变化代表新的需求版本，不继承旧版本误报。旧记录与来源快照保留；仍未处理的旧项标明历史来源，不能静默宣称完成。

持久化审核条目及处理事件，引用报告/需求版本，不复制完整 AI 报告。报告保存和待办归并在一个事务内完成；用户处理采用 revision 乐观并发。模型晚返回时在事务中读取当前人工状态，不覆盖用户刚作出的误报或完成决定。重复保存同一报告具有幂等性。

## 4. 原文区域的默认错误

移除“显示该项目最近任意任务错误”的逻辑。未配置材料、尚未审核、没有原文等初始状态使用普通引导，不使用红色错误。

需求页面只显示当前需求操作的真实错误及本次需求任务状态；BUG、日志下载及历史任务错误通过统一任务列表查看。真实解析失败、权限失败和来源缺失仍明确展示，不通过删除 catch 或隐藏所有错误来掩盖。

## 5. 独立资料库与多级分类

### 5.1 分类树

资料库采用分类树与当前分类内容区：可新增根分类/子分类、重命名、移动，支持“需求 / UI / UE / 通用资料”等用户自定义层级。项目名称可作为分类名称，但分类不要求存在代码仓库，也不自动绑定代码项目。

提供“全部资料”和“未分类”入口及名称/路径/链接搜索。移动或重命名分类不改变资源 ID、项目关联或内容快照。后端拒绝循环父子关系和非法分类引用；有资料或子分类的分类须先移动内容后才能删除，不静默级联删除。

### 5.2 资料类型与保存

支持现有 DOCX、PDF、飞书文档，以及通用网页链接、本地文件/目录路径、文本说明。保留资料名称、所属分类、用途（需求/UI/UE/通用）、地址或文本、备注等明确字段。

保存资料不要求项目、代码路径或 AI 连接。普通路径或目录条目只保存引用，不要求该路径当前已存在；读取时才明确检查。通用链接和路径不会自动成为可解析需求，不把未支持的 UI 页面、目录或外部网址交给现有 Word/PDF 解析器。

飞书中可读取的需求文档继续走已有 CLI；UI/UE 链接可以先作为参考资料保存。纯文本说明作为独立资料保存，本阶段不自动从备注推断需求。未支持解析的内容明确标为参考资料。

### 5.3 唯一资源和可选关联

资源独立保存，代码项目通过稳定资源 ID 可选关联。同一资源可服务多个项目，解除关联不删除资料；没有项目时完整支持分类和资料增删改查。

沿用一份规范资源存储，不建立另一个“通用资料库副本”。将现有资源扩展为区分可解析文档和参考资料的联合类型，现有文档 API 可保留为可解析资源投影。分类元数据不参与内容版本哈希，移动分类不触发需求重新审核。

项目关联统一引用资源 ID，并区分“审核需求”和“参考资料”；现有 documentRefs 迁移为审核需求关联，运行时 project.documents 从可解析审核资源派生。只保留一套规范关联记录，不同时持久化两套项目文档关系。参考资料不进入必须解析的材料清单；需要审核的资料读取失败仍按 required 规则报错。

## 6. 连接设置收拢

“BUG 平台连接”下分 Jira / Trinity 二级分组；“AI 连接”独立分组。初始只显示已保存条目的名称、必要身份/项目摘要和默认标记，以及“新增”入口；空列表显示空状态。

连接详情、编辑表单均在二级内容中展开，默认收起。主动新增时才打开完整新增表单；主动编辑时才打开现有连接表单。保存或取消后收起，清空尚未保存的密码输入。不在进入设置时自动展开新增表单、执行模型探测或报登录错误。

复用现有登录、Codex CLI 发现/模型选择和连接删除逻辑。编辑保留连接 ID 和项目引用；AI 删除继续提供受影响项目及替代/解除关联选择，不新增隐式替代 AI。Jira 每条连接对应一个 Jira 项目且可多条；Trinity 唯一账号和自动关联全部代码项目的规则不变。

项目编辑器中复用相同连接编辑能力；列表容器和按需表单不能再维护两套登录流程。飞书 CLI 的功能沿用现状，本次重点收拢 Jira、Trinity 和 AI 连接。

## 7. 迁移、模块边界和验证

涉及 renderer 的 RequirementsPage、DocumentsPage、DocumentLibraryPage、DocumentResourceEditor、ProjectDocumentsDialog、IssueConnectionsPage、ConnectionsPage；contracts/IPC/preload；core 的 TaskService、需求审核/归并服务；storage 资源/分类/审核状态及迁移。

数据迁移先备份，保留旧资源 ID、项目关联、报告、需求版本和 AI/BUG 连接。旧资源进入“未分类”，现有需求关联继续有效。新结构提升 schema 版本，拒绝旧客户端误读，避免 1.0.1 覆写新结构。

关键验证：

1. 无 AI 时不能发起审核；有 AI 时读取当前代码及未提交修改，git fetch/pull/rebase/synchronize 调用数为零，工作区和分支不被修改。
2. 待确认条目不预选，误报直接处理后隐藏；未完成必须确认后出现完成选项；失败不隐藏；刷新/重启保留状态。
3. 相同报告不重复归并；同版误报保持隐藏；完成后重检缺失重新打开；AI 改判已实现不代替人工完成；多项目不串条目。
4. 初始页无默认红色错误；BUG/日志任务错误不泄露到需求原文，真实需求读取错误仍可见。
5. 零代码项目时可创建多级分类并保存飞书 UI/UE 链接、通用路径和文本；分类移动不改项目引用；循环和非法删除被拒绝。
6. 设置初始没有新增表单，新增/编辑才展开，保存/取消收起；删除与关联、CLI 模型发现、Trinity 唯一账号行为回归通过。
7. 隔离数据库迁移、单元测试、类型检查、lint、桌面回归及本地打包通过；已发布 1.0.1 的文件和标签不被覆盖。

本设计不改变此前确定的网络策略，不把在线更新下载链路优化混入本次四项调整。
