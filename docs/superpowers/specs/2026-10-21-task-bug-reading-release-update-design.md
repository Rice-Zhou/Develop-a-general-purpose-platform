# 任务导航、BUG 报告阅读与客户端在线升级设计

日期：2026-10-21。开发根目录：`D:/development/Develop-a-general-purpose-platform`。

当前基线：0.9.3。建议本批交付版本：0.10.0。

## 1. 目标与确认的信息

本次修改围绕五个体验目标：统一任务入口、报告跟随 BUG、证据原位展开、优先阅读问题原因、从 Release 检查与安装新版。

用户已指定更新来源为公开仓库：
`https://github.com/Rice-Zhou/Develop-a-general-purpose-platform`。

默认使用此公开仓库，无需 Token。当前仅实现 GitHub 来源；更新服务保留供应商接口，后续有真实需求再接 GitLab，不增加第二套未使用实现。

本次是跨模块设计：前四项复用已有持久数据和分析流程，第五项增加更新模块。本文需评审通过后再细化实施计划和进行实现。

## 2. 现状与需要保持的不变量

当前任务表混合展示活动任务与历史，BUG 工作台又有独立任务列表。报告历史按代码项目展示，没有将每个列表项与原始 BUG 的稳定身份关联。报告页将复现条件、代码事实、候选原因都平铺显示，所有证据共用一个位于页面底部的 excerpt 状态。

发行已生成 Squirrel 安装包和便携 ZIP，但没有版本检查、下载状态或安装交接流程。

保持以下不变量：

- 任务仍由现有 TaskService 和独立日志队列管理；不引入另一任务队列或历史数据源。
- 报告仍保存在 bug_reports，并引用原始 issue_snapshots 和固定上下文；不复制出第二份“BUG 分析记录”。
- BUG 身份不能使用会在刷新时变化的快照 ID，也不能只用问题标题或展示单号。
- 阅证仍走 readEvidence，受现有项目、固定快照和哈希校验约束。
- 更新检查与下载沿用直连网络，不使用 AI 代理，不降低 HTTPS，也不关闭 TLS 校验。
- 没有用户选择更新时，不下载执行文件、不关闭程序、不安装；有活动任务时不强制安装。

## 3. 任务列表和任务历史

侧边栏一级菜单改为“任务列表”，显示活动任务数量。历史作为该菜单下可展开的二级入口，默认收起，不在未选中时渲染历史记录。

行为定义：

- 点击一级“任务列表”，展示 QUEUED、PREPARING、RUNNING、VALIDATING、CANCELLING，以及需要继续处理的 WAITING_INPUT。
- 展开一级菜单的箭头后出现“任务历史”二级菜单；点击它才展示 SUCCEEDED、FAILED、CANCELLED、INTERRUPTED。
- 收起历史菜单时，若正处于历史页，回到当前任务列表，避免选中不可见菜单。
- 开始/取消/重试/删除的权限继续复用后台规则，任务类型和 BUG 单号仍显示。
- 失败任务计数可提示用户进入历史，但不自动展开历史。总览不再平铺已结束的最近任务，仅保留当前任务摘要和进入任务列表的入口。
- 移除 BUG 工作台中重复的完整任务列表，保留每张问题卡自己的提交/排队/分析状态及“查看任务”入口；该入口跳到统一任务列表，并携带项目及问题筛选。

任务详情仍使用现有详情组件；本次不另建任务数据表。任务状态变化后，条目从当前列表移动至历史，不重复占位。

## 4. BUG 与报告绑定及二级页面

每张 BUG 卡片在预分析按钮旁新增“打开分析报告”。

报告关联使用原有报告对应的问题快照，按“分析代码项目 ID + 来源连接 ID + 远端问题 ID”定位。来源连接区分平台和实例；代码项目 ID 区分同一个 Trinity BUG 对多个代码项目的分析。绑定不能依赖刷新后新生成的 issueSnapshotId，也不将 A 项目的报告显示给 B 项目。

读取逻辑由后端一次性计算报告摘要或按身份查询，避免渲染器逐条读取整份报告和形成 N+1 请求。读取权限复用当前项目和来源边界。现有成功报告直接通过原始快照关联，不要求用户重新分析，不增加平行缓存或复制历史。

按钮行为：

| 当前状态 | 点击结果 |
| --- | --- |
| 没有报告，也没有活动分析 | 提示“当前问题还未分析，可先执行预分析” |
| 没有报告，分析排队或执行中 | 提示“当前问题已在分析列表中”，提供查看任务入口 |
| 有成功报告 | 进入二级页面“BUG 分析报告”，默认最新成功版本 |
| 有旧报告，同时新任务运行 | 旧报告仍可读，标明生成时间和新分析状态 |
| 分析失败且没有成功报告 | 明确失败状态，提供任务详情或重新分析入口 |

报告页在 BUG 工作台下以二级页面/面包屑展示，返回时保留原项目和问题阅读位置。一个问题有多个成功报告时，版本选择放在该问题的报告页中；取消独立的项目级“BUG 报告历史”面板。

任务历史中的已完成 BUG 分析也可进入同一报告页面，保证问题后续关闭、不在活动 BUG 列表时，历史报告仍可阅读。删除任务历史记录仍不删除报告，沿用现有行为。

## 5. 报告默认阅读顺序与证据展开

报告顶部保留问题号、标题、报告时间及简短静态预分析标识。主体首先展示“候选原因与排查步骤”；没有候选原因时明确显示暂未形成有依据的候选原因。

其余全部默认收起，用户点击后才展示：

- 复现条件；
- 代码事实；
- 待补充信息；
- 固定版本证据；
- 分析版本、模型和用量、检查范围及未解析材料。

候选原因中保留可点击的支持/反对证据入口，详细证据内容仍按用户操作展示，不默认平铺长 ID 列表。

每条证据拥有独立的展开/加载/错误状态：点击“阅读证据”就在该条目下方插入内容，其余条目自然向下排列；再次点击可收起。允许多条同时展开。请求按报告 ID 和证据 ID 隔离，切换报告后旧请求不能把内容写入新报告。失败消息位于对应条目，并允许重试；不会再共用页面最底部的单个代码预览。

## 6. 在线升级方案选择

比较两种方案：

1. **采用完整安装包更新（本次推荐）**：直接利用 GitHub Release 中的现有 Squirrel Setup.exe，平台负责检查、用户选择、下载、哈希校验及安装交接。安装版和当前便携版共用下载及校验流程，维护成本较低。便携版首次在线升级会明确转为安装版，保留相同 userData；下载体积较大。
2. **原生 Squirrel 自动更新**：安装版利用 RELEASES/nupkg 更新，未来可利用增量包；便携版仍需单独处理。还需要处理原生下载通道的网络策略与发布元数据，当前不采用这套额外流程。

本次选择方案 1，不叠加第二套下载器。已有便携版可继续直接启动；只有选择在线安装更新时才转为安装版，安装前显示该说明。本次 0.10.0 本身需要先手动安装/启动一次，旧的 0.9.3 不具备主动更新能力。

### 6.1 检查与提示

- 默认仓库固定为用户提供的公开仓库，设置中显示来源及版本，用户无需配置 Token。
- 主进程在每次应用进程启动后检查一次。托盘恢复、页面切换、渲染器刷新不重复触发启动提示。
- 只接纳正式 Release；忽略 draft/prerelease，按语义版本比较，版本必须大于当前客户端版本，不能自动降级。
- 发现新版后仅弹一次提示：当前版本、新版本、更新说明、“更新”“暂不更新”。选择暂不更新后本次进程不再自动提醒。
- 设置页新增“客户端更新”：当前版本、检查更新、检查结果、下载进度、取消下载、已下载待安装及错误信息。手动检查不受启动一次限制。
- 没有新版时，启动检查不弹窗；用户手动检查则显示“当前已是最新版本”。网络错误只在设置中显示，启动时不反复弹错误窗口，不将错误伪装成已是最新。

### 6.2 Release 素材约定

打包结束后生成与实际安装器对应的 `platform-update.json`，与 `LocalDevPlatformSetup.exe` 一起作为同一 GitHub Release 的附件。清单字段包括 schemaVersion、version、platform、arch、assetName、size、sha256。客户端用 Release 附件列表解析真实下载地址，不执行清单中的任意命令或路径。

tag、清单版本、应用 package.json 版本必须一致；附件必须满足 Windows/x64 和既定文件名要求。缺少清单、版本不一致、包不完整、大小或哈希不符都明确提示，不提供安装按钮。

清单和安装包必须来自配置仓库同一 Release 的 HTTPS 附件，下载只允许 GitHub 合法附件重定向。更新说明作为普通文本显示。接收端始终校验版本、大小和 SHA-256；不使用 AI 连接凭据，也不在客户端内保存发布权限。

本次只生成可发布素材和发布说明，不因设置了仓库地址就上传代码或发布 Release。实际发布需另有用户明确指令。

### 6.3 下载和安装交接

- 主进程拥有唯一更新状态，渲染器仅展示；重复点击共用同一次检查/下载，不产生多个安装器进程。
- 用户选择更新后才下载到平台更新缓存，先写临时文件，大小与 SHA-256 通过后再标记可安装；取消或下载失败不能留下可执行的成功状态。
- 下载期间可以继续任务。点击“安装并重启”时重新核对当前更新信息、包哈希和本地缓存路径，渲染器不能传入任意 exe。
- 安装前若有排队、准备、分析、校验、取消中的任务，说明需先完成/取消，提供前往任务列表入口，不静默杀任务。
- 确认安装后先冻结新任务进入，再原子检查忙状态；若出现活动任务则解除冻结并提示等待。空闲时使用现有 shutdown 等待任务/监控/日志服务结束并关闭数据库，再将执行权交给已经校验的安装器。启动安装器失败必须明确显示错误和重新启动客户端入口；已经停止的后台服务不能被界面伪装为仍可使用。交接失败不记为更新成功；安装器启动不等同新版已运行。
- 对 Squirrel 安装启动事件单独处理，不能在安装事件中启动普通工作台、定时监控或重复登录。普通新版启动仍使用相同 userData，按现有数据库升级规则备份。

### 6.4 当前接入事实

设计阶段从本机直连 GitHub API，仓库及 Release 查询均返回 HTTP 403，尚不能据此确认仓库当前有无正式 Release。实现应将访问受限与无 Release/无新版区分。后续验证需记录真实服务结果，不使用模拟结果冒充公开 Release 联调成功。

## 7. 影响范围

- App.tsx、任务页面/导航：统一活动任务与二级历史路由，复用任务来源。
- BugsPage.tsx、BugReportPage.tsx：每问题报告入口、二级页、报告布局及局部证据展开；删除废弃独立报告面板和重复任务列表。
- 现有问题仓储/Workbench/IPC/contracts：查询问题关联报告摘要，继续使用原有报告表与快照关系。
- main/preload/contracts：更新检查、下载状态和安装交接的受限接口；新增主进程 UpdateService 与 GitHub Release 适配器。
- forge 打包及发行脚本：从最终产物生成更新清单，给出公开 Release 素材及上传步骤。
- 设置页、样式、README 和验收记录。

不预设新数据库表；若实现发现需要存储内容，优先复用 settings 和现有报告关系，不能产生第二份报告或任务真相。

## 8. 验收标准

1. 启动后侧边栏只有一级任务列表；二级历史默认收起，未选择时页面没有历史内容；取消、重试及删除行为与后台一致。
2. A/B 两个 BUG 的报告互不混淆；无报告/排队/有报告/旧报告更新中四种状态可验证；刷新问题快照后旧报告仍可读；多代码项目隔离；现有真实成功报告能从对应 BUG 进入。
3. 报告默认只展开原因和步骤；复现、代码事实及其他内容均需用户展开；进入证据区后多条证据可各自原位展开，错误及慢响应不会串条目或串报告。
4. 启动新版提示在同一主进程最多一次，暂不更新不重复弹；设置中可手动检查；下载前不取包；取消、网络错误、403、无正式 Release、损坏包均有准确结果。
5. 活动任务存在时可下载、不可安装；包版本/大小/哈希必须正确；从安装版/便携版识别到对应说明；安装交接失败不显示成功；配置与历史保留。
6. 单元测试覆盖报告身份、版本比较、Release/清单契约、一次提示状态和校验失败；桌面测试覆盖导航、BUG 报告绑定、证据展开及更新交互。类型检查、lint、打包和发行文件核对通过后交付。
7. 真实 Release 检查与实际安装更新另行记录；公开 API 受限、Release 未发布或未进行实际安装时，明确说明验证边界。
