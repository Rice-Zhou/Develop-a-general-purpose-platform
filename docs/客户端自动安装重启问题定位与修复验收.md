# 客户端自动安装与重启：问题定位和修复验收

日期：2026-10-22。用户要求继续定位自动安装及重启问题，并在 GitHub 限流恢复后重新验证完整在线更新。工作目录为 `D:/development/Develop-a-general-purpose-platform`。

## 结论和边界

确认两个独立问题：首次联调改写系统用户目录导致安装验证失真；正式安装辅助进程泄漏 Node 模式，导致安装完成后客户端未正常启动。生产修复仅清理安装器子进程的 `ELECTRON_RUN_AS_NODE`，不改更新源、下载校验、项目数据、Windows 用户目录或代理规则。

**源码修复已完成，真实缓存安装包的自动安装及重启已通过；公开更新源的完整下载到重启流程待 GitHub 匿名额度恢复后重验。修复尚未发布，现有 v1.0.3 标签和附件未覆盖，不宣称已发布的 1.0.3 安装包包含此修复。**

## 根因一：联调脚本改写 Windows 用户目录

前一轮脚本同时将 APPDATA、HOME、USERPROFILE 指向平台隔离目录。使用实际 Windows PowerShell/.NET 只读对照：正常环境的 `Environment.GetFolderPath(LocalApplicationData)` 返回真实用户 Local 目录；改写 USERPROFILE 后该值为空。Squirrel 依赖系统用户目录定位安装位置，不能用这类环境模拟正常桌面升级。

修正联调方式：仅设置平台自有的 `PLATFORM_DATA_DIR`，保留系统用户目录。独立资料仍使用空的测试数据和显式本地夹具，不复用个人 AI 凭据。该修正只涉及本地联调脚本，产品无需增加用户目录回退逻辑。

证据：`out/update-handoff-investigation/known-folders.json`。

## 根因二：安装器继承辅助进程 Node 模式

`InstallerHandoff.prepare` 需要以 `ELECTRON_RUN_AS_NODE=1` 启动独立 JS 辅助进程。原 `spawnDetached` 将整个环境直接交给安装器，该变量继续传给安装器随后启动的 Electron 客户端。安装器可成功结束，新客户端却按 Node 方式运行。

对同一个已校验的正式 1.0.3 安装包，保留真实 Windows 用户目录，使用独立平台数据进行真实对照：

| 环境 | 安装器退出 | 安装后客户端 |
| --- | --- | --- |
| 携带 ELECTRON_RUN_AS_NODE=1 | 0 | 未创建平台数据库，未出现客户端进程/界面 |
| 移除 ELECTRON_RUN_AS_NODE | 0 | 自动创建 schema 13 数据库，出现正常客户端进程 |

证据：`installer-environment-matrix.json`、`restart-environment-matrix.json`，均位于上述本地证据目录。两组均运行真实安装程序，没有替换下载、校验或响应。

## 源码修复

- `apps/desktop/src/main/update-helper.ts`：启动安装器或恢复旧客户端时，在统一的子进程启动边界复制环境并移除 Node 模式；保留 `PLATFORM_DATA_DIR` 等其他变量，不修改传入环境。
- 删除恢复旧客户端分支中重复的环境处理。运行辅助进程自身所需的 Node 模式仍在父进程 `InstallerHandoff` 中显式设置。
- `apps/desktop/src/main/update-helper-process.test.ts`：验证显式环境和默认继承环境均不会泄漏 Node 模式，原环境不变，启动错误明确抛出。先复现失败断言，再应用修复。

当前行为仍区分“安装器已启动”和“已升级成功”；只有新版本实际启动并达到目标版本，结果读取才显示成功。
