# 0.3.2 项目配置、平台登录与网络隔离

## 用户要求与实现

1. 平台登录和项目范围分开。设置中只展示 Jira、Trinity 两类平台，Jira 自动检查本地 CLI 及已有登录，成功时显示真实实例和账号；无可用配置则进入账号登录。项目中显示 Jira / Trinity 添加入口及项目 Key、负责人和缺陷类型，仍由同一 ScopePolicy 验证范围。
2. 默认一个主仓库；只有点击添加才出现关联仓库。原有读取当前分支、确认采用、自定义目标分支及同步安全检查保留。
3. 新建项目保存成功后提示“配置 BUG AI 预分析”，可跳过或直接聚焦 AI 设置。项目已经保存，不自动分析；编辑既有项目不重复提示。AI 连接保存后仍需在项目关联。
4. 普通访问统一直连，AI 每连接可选代理。没有全局环境或全局 dispatcher 写操作，代理失败不回退到另一网络路径。

## 登录与凭据

Jira 账号方式是用户本轮补充后新增的显式 Server / Data Center 适配方式，依据 [Atlassian Basic authentication 文档](https://developer.atlassian.com/server/jira/platform/basic-authentication/)。先验证 /rest/api/2/myself，再使用既有主进程加密凭据存储；Cloud 仍使用 CLI。两种 Jira 适配器复用规范化、JQL、问题编号和范围规则，没有按失败自动切换身份或传输。

Trinity 依据用户提供的 [目标实例](https://trinity.desaysv.com/) 和本机既有接口资料核对公开前端。当前公开脚本确认 LDAP 路径及 AES-CBC 协议；实现只读取同源有限 app 脚本并提取公开协议参数，不执行脚本，不硬编码密钥。未识别协议时在发送账号密码之前停止。只在登录成功后保存 token；不保存 Trinity 密码。旧 token 连接继续复用同一问题读取适配器。

该站 Node TLS 协商失败，而系统 curl 使用 Windows 证书验证可成功访问。Trinity 采用系统 curl.exe 的原生 TLS，不关闭证书验证或启用旧 TLS 的全局开关。禁用 curlrc 和代理，不跟随重定向，认证头及请求正文只通过 stdin 传递，响应和执行时间有界。缺少系统 curl 时显式失败。

真实站点仅执行公开登录协议探测：读取 5 份公共内容确认协议，在登录 POST 前主动停止；没有发送真实账号密码。真实 Trinity 账号、会话过期行为及完整 BUG 字段仍需用户在设置中实际验证，项目列表契约仍未确认，因此不能批量读 Trinity。

## 网络边界

- 普通子进程移除大小写代理环境，设置明确直连；Jira CLI 不再允许通过旧 bypassProxy=false 继承代理。
- Git 按次覆盖通用、URL 专属及 remote 代理配置。SSH 使用 OpenSSH 并按次禁用 ProxyCommand 和 ProxyJump，保留主机及 IdentityFile 配置；不执行自定义 GIT_SSH 脚本，也不改用户文件。
- HTTP 模型使用 undici 7.30.1 的请求级 Agent / ProxyAgent，旧配置缺少 proxyUrl 也默认直连。订阅代理只进入对应子进程；第三方工具自身强制代理配置的限制在界面明确展示。
- 代理地址只支持不含凭据的 HTTP(S) URL，进入执行配置哈希；不会影响 Jira、Trinity、飞书、Git 或另一 AI 连接。

## 实施取舍

- Jira CLI 优先，账号登录是用户本轮明确要求的独立选择，不按失败静默重试另一认证方式；Jira Cloud 没有伪造密码登录支持。
- Trinity 登录参数随目标站公开前端解析，避免硬编码密钥；代价是站点改版可能显式停止，需要更新已验证协议。
- 统一普通网络直连覆盖自定义 SSH 命令；特殊 SSH 身份参数请放入正常的 SSH 主机配置，平台不会执行自定义 transport 脚本。
- 自动监控、Trinity 项目列表、真实模型质量和真实账号验收仍按既有门槛推进，不因本次配置优化宣称已经完成。
